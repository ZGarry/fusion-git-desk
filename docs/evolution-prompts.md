# Fusion Git Desk 持续迭代提示词

状态日期：2026-06-11

本文档用于驱动 Fusion Git Desk 的持续迭代工作流。它不再按“每天必须做一次改动”来运行，而是按“每次触发先分析当前最值得优化的方面，再选择一个小而完整的目标”来运行。第一目标仍然是把基础能力做稳：多仓库扫描、状态识别、安全同步、diff 巡检、小步提交、可验证发布。

## 项目核心定位

Fusion Git Desk 是一个轻量的多仓库 Git 运维台。它帮助用户在一个桌面窗口里回答：

- 当前哪些仓库有变化？
- 哪些仓库落后、领先、冲突、没有 upstream 或有本地改动？
- 哪些仓库可以安全 fetch 或 fast-forward pull？
- 选中仓库里具体改了什么，能否安全地 stage、unstage 和 commit？

它不替代 IDE，不追求覆盖全部 Git 命令，也不优先做复杂平台化能力。当前阶段优先保证基础闭环可信、清楚、可验证。

## 基础优先原则

- 每次只选择一个小而完整的目标。
- 基础闭环有 P0/P1 缺口时，不做深层优化、不做大功能、不做提前抽象。
- 自动化可以提出需求和实现改动，但必须先给出问题价值和验收方式。
- Git 写操作必须显式、可追踪、可回滚。默认直接在 `main` 上本地提交；只有全部验证通过后才允许推送 `origin/main`。
- 常规迭代固定在 `main` 完成，实现、验证、提交、推送都不离开主干。
- 每轮工作都要更新 `WORKDOC.md`，按日期追加简短工作记录。
- 保持项目约束：Go + Wails v2 后端，Vue 3 + TypeScript + Vite 前端，Git 操作通过系统 `git`，Windows 下 Git 子进程保持隐藏窗口启动。

## 基础闭环检查

选题前先检查下面 6 个问题。任何一项存在 P0/P1 缺口，都优先修基础能力：

1. 扫描：能否发现工作区内多个仓库，并清楚处理空目录、权限错误、嵌套仓库和 Git 命令失败？
2. 状态：分支、远端、ahead/behind、本地改动、staged 文件、冲突、upstream 是否可信且可解释？
3. diff：working/staged/HEAD、文件级 diff、未跟踪文本、二进制或过大文件是否有稳定展示或明确说明？
4. 同步：fetch、pull、自动 pull 的边界是否清楚？脏仓库是否被保护？pull 是否固定 `--ff-only`？
5. 提交：stage/unstage/commit 是否只作用于当前仓库和明确文件？失败原因是否可理解？
6. 验证：本轮改动是否能通过自动测试、构建、手动验收或发布检查证明？

## 什么问题值得优化

优先级判定：

- P0：会破坏用户工作区、导致数据丢失、构建测试发布失败、核心流程无法使用的问题。
- P1：用户在常规多仓库巡检中反复遇到的卡顿、误解、错误不可见、安全边界不清或操作闭环断裂。
- P2：明确提升效率但不影响基础闭环的体验改进，例如过滤、排序、轻量提示、文档补强。

暂缓处理：

- 没有用户场景或测量依据的深度性能重构。
- 为未来大功能提前铺设的大抽象。
- 会扩大 Git 写操作范围但缺少保护、测试和回滚路径的功能。
- 只让内部结构更漂亮，但不改善用户基础流程的改动。
- 一次同时触碰多个模块、难以验证成败的“大而全”目标。

## 单次迭代 Loop

1. 读上下文：`AGENTS.md`、`README.md`、`WORKDOC.md`、`docs/requirements.md`、`docs/roadmap.md`、`docs/performance.md` 和当前 git 状态。
2. 分析候选：按“基础闭环检查”和 roadmap/performance 文档列出当前最值得优化的 3-7 个候选，说明优先级、价值、风险和验收方式。
3. 选择目标：只选 1 个排名最高、范围最小、能验证的问题；如果没有值得做的问题，只输出分析报告，不制造改动。
4. 定义问题：写清用户场景、为什么值得本轮处理、涉及文件、非目标。
5. 定义验收：先写验证方式，再实现。没有验收方式的问题不要进入实现。
6. 小步实现：遵循现有代码风格，避免无关重构和跨模块扩大。
7. 验证：按影响范围运行自动门禁和手动检查。
8. 记录：更新 `WORKDOC.md`，必要时更新对应需求、roadmap 或性能记录。
9. 发布：只有验证通过才提交并按 `RELEASE_MODE` 发布。

## 验证策略

最低门禁：

- 代码改动：尝试运行 `cd frontend && pnpm build` 和 `go test ./...`。
- 文档改动：运行 `git diff --check`，并检查相关文档标题、定位、验证规则是否能被搜索到。
- 发布或打包改动：额外尝试 `wails build` 或对应脚本；Windows 无法生成 macOS 包时说明限制。
- Git 操作改动：必须覆盖干净仓库、脏仓库、无 upstream、冲突或失败路径中的相关场景。
- UI 改动：除构建外，尽量做一次本地界面检查，确认按钮禁用、错误提示、空状态和文本不互相遮挡。

验证输出必须包含：

- 运行了哪些命令。
- 哪些手动场景已检查。
- 哪些检查因环境缺失无法完成。
- 失败时的最小修复或回退建议。

## 变量

复制提示词时可替换这些变量：

```text
REPO_PATH=E:\my\fusion-git-desk
RUN_CONTEXT=本轮迭代说明
RELEASE_MODE=main-direct
```

`RELEASE_MODE` 建议取值：

- `main-direct`：默认模式。直接在 `main` 上提交并推送到 `origin/main`，触发远程 macOS 打包 workflow。
- `tag-release`：正式发布模式。所有验收通过后更新版本和 changelog，创建并推送 `v*` 标签。
- `local-only`：只做本地改动和报告，不推送。

常规迭代统一使用 `main-direct`，直接在当前主干完成实现、验证和推送。

## 总控提示词

```text
你是 Fusion Git Desk 的持续迭代代理。请在 REPO_PATH 仓库中工作。本轮目标不是按日期例行制造改动，而是先分析当前最值得优化的方面，再选择一个小而完整、可验证、可发布的改进。

项目背景：
- Fusion Git Desk 是 Wails v2 桌面应用，用于管理多 Git 仓库工作区。
- 后端是 Go package main。
- 前端是 Vue 3 + TypeScript + Vite。
- Git 集成通过系统 git 和 os/exec 完成。
- 自动 pull 必须只作用于干净仓库，除非用户明确选择其他策略。
- Windows 下 Git 子进程必须隐藏窗口启动。

工作要求：
1. 先读取 AGENTS.md、README.md、WORKDOC.md、docs/requirements.md、docs/roadmap.md、docs/performance.md、docs/daily-evolution-prompts.md 和当前 git 状态。
2. 按“基础闭环检查”先判断扫描、状态、diff、同步、提交、验证是否存在 P0/P1 缺口。
3. 如果基础闭环存在 P0/P1 缺口，本轮只处理其中一个最小可验证问题。
4. 如果基础闭环健康，再从 roadmap 或 performance 中选择一个有明确用户价值和验收方式的小目标。
5. 不要选择没有复现、没有测量、没有用户场景的深层优化。
6. 实现前必须先输出候选分析：列出 3-7 个当前值得优化的方面，标注 P0/P1/P2、为什么值得做、涉及文件、风险和验收方式。
7. 从候选中只选择 1 个排名最高且范围最小的目标；如果没有值得做的目标，只输出分析报告并停止。
8. 写出简短计划，包含问题、非目标、涉及文件和验收方式。
9. 实现时遵循现有代码风格，避免无关重构、锁文件 churn 和发布产物 churn。
10. 修改后运行可用质量门禁，至少尝试：
   - cd frontend && pnpm build
   - go test ./...
11. 如果只是文档改动，至少运行 git diff --check，并检查核心定位、选题闸门和验证规则是否写入对应文档。
12. 如果本机缺少 Go、Node、pnpm、Wails 或远程凭据，记录阻塞原因，并尽可能完成可验证的部分。
13. 更新 WORKDOC.md，按日期追加简短工作记录。
14. 通过验证后按 RELEASE_MODE 发布：
   - main-direct：提交到本地 main，推送到 origin/main；如果远程凭据缺失，保留本地提交并记录阻塞原因。
   - tag-release：确认版本号，更新必要版本记录，提交，推送 main，创建并推送 v* 标签。
   - local-only：只保留本地提交或改动报告，不推送。
15. main-direct 模式不创建 PR；即使 gh CLI 可用且已登录，也只用于查询 workflow 或发布状态，除非用户本轮明确要求分支/PR 模式。
16. 最终输出：本轮候选分析、选择的目标、为什么值得做、改动摘要、验证结果、发布结果、后续建议。
```

## 单次分析提示词

```text
请对 Fusion Git Desk 做一次单次迭代分析，只输出高信号结果，不要开始实现。

先检查基础闭环：
1. 扫描：仓库发现、空目录、权限错误、嵌套仓库、Git 命令失败反馈。
2. 状态：分支、远端、ahead/behind、本地改动、staged、冲突、upstream。
3. diff：working/staged/HEAD、文件级 diff、未跟踪文本、二进制、过大文件。
4. 同步：fetch、pull --ff-only、仅干净仓库自动 pull、失败说明。
5. 提交：stage/unstage/commit 的范围、失败提示、刷新结果。
6. 验证：测试覆盖、构建、发布链路和文档是否与代码现状冲突。

再列出最多 7 个候选事项，按 P0/P1/P2 排序。每项包含：
- 问题
- 为什么值得优化
- 涉及文件
- 非目标
- 预估风险
- 建议验收方式

最后只推荐本轮最适合自动完成的 1 个事项。如果没有值得做的 P0/P1/P2，建议本轮只输出分析报告，不要制造新改动。
```

1. 需求名称

3. 问题优先级：P0/P1/P2
4. 为什么值得现在做
5. MVP 范围
6. 非目标
7. 涉及模块
8. 验收标准
9. 风险与回滚策略

## 实现提示词

```text
请实现以下已选需求：<填写需求名称和验收标准>。

执行规则：
- 先阅读相关文件，不要凭空改代码。
- 先确认该需求通过了基础闭环和选题闸门。
- 后端优先使用结构化 Git 输出，例如 git status --porcelain。
- 所有长耗时 Git 命令必须有 timeout。
- Windows Git 子进程必须继续使用隐藏窗口启动。
- 前端遵循现有 Vue 组件和 CSS 风格，不引入不必要依赖。
- 性能相关改动必须说明避免了哪些重复计算、阻塞 I/O 或过量 DOM，并说明证据来源。
- 不要改动无关格式、锁文件或发布产物，除非本需求需要。

完成后运行：
- cd frontend && pnpm build
- go test ./...

如果只是文档改动：
- git diff --check
- 检查核心定位、选题闸门、验证规则是否在对应文档中可找到。

如果验证失败，先修复；如果环境缺失导致无法运行，说明缺失项和可替代验证。
```

## 性能优化提示词

```text
请对 Fusion Git Desk 做一次性能导向的小步优化。先判断是否真的值得做。

只有满足以下任一条件才进入实现：
- 用户在扫描、diff、fetch/pull、stage/commit 中明显感到卡顿。
- 已有耗时指标或代码阅读证明存在重复 Git 命令、重复遍历、重复请求或过量 DOM。
- 改动能降低后台任务重叠、Git 子进程堆积或界面冻结风险。

重点观察：
- 多仓库扫描时每个仓库的 Git 命令数量和耗时分布。
- git status、diff、branch、remote、log 是否可以减少调用或延迟加载。
- 未跟踪目录、大 diff、大量变更文件是否会造成磁盘读取或 DOM 爆炸。
- 前端 computed/watch 是否有重复遍历、竞态覆盖或高频后端写入。
- 自动刷新、自动 fetch、自动 pull 是否可能重叠执行。

请选择一个风险可控的优化点完成实现，并在 docs/performance.md 中追加记录：
- 触发场景
- 优化前的问题
- 采取的策略
- 性能取舍
- 验收方式

如果没有证据支持，不要实现深层优化，只输出观测结论和建议验证方式。
```

## 发布提示词

```text
请把本轮已验证改动发布到远程。

发布前检查：
1. git status --porcelain，确认只有本轮相关改动。
2. 确认已经完成与改动类型匹配的验证：
   - 代码改动：cd frontend && pnpm build；go test ./...
   - 文档改动：git diff --check；核心定位、选题闸门、验证规则可搜索到。
   - 打包或发布改动：额外尝试 wails build 或相关脚本。
3. 更新 WORKDOC.md，按日期追加本轮简短工作记录。
4. 阅读最近提交和版本号，判断本次是普通远程发布还是正式 release。

默认发布流程：
- 确认当前位于 main。
- 提交信息使用：type(scope): summary。
- 直接推送到 origin/main。
- 推送后检查 GitHub Actions 的 macOS package workflow，确认远程打包是否已启动或完成。
- 发布流程固定使用 main。

正式 release 流程只在明确要求 RELEASE_MODE=tag-release 时执行：
- 确认新版本号。
- 更新版本记录和必要文档。
- 推送已验证的 main。
- 创建 v* 标签并推送。
- 等待 GitHub Actions 生成 Release artifact，报告 workflow 结果。

不要在未通过验证时推送 release 标签。
```

## 故障处理提示词

```text
本轮自动演化失败了。请做恢复分析，不要继续扩大改动。

请输出：
1. 当前 git 状态。
2. 已修改文件列表，以及哪些是本轮产生的。
3. 失败发生在哪一步：读取、选题、实现、构建、测试、手动验收、提交、推送、CI、release。
4. 是否违反了基础优先原则，例如在基础闭环未稳定时选择了深层优化。
5. 最小修复建议。
6. 是否需要回滚本轮改动。
7. 如果需要回滚，只给出候选命令，不要自动执行 destructive 命令，除非用户明确授权。
```

## 建议节奏

- 每次触发：先分析当前最值得优化的方面；最多完成一个小改进；验证通过后主干提交并推送。
- 周期整理：定期整理 roadmap，关闭过期需求，挑一个 P1 基础能力补强。
- 性能审计：在有真实卡顿、指标异常或用户反馈时执行，重点看扫描耗时、diff 渲染和后台任务拥堵。
- 每个正式版本：只在所有门禁通过后推送 `v*` 标签，让 GitHub Actions 生成 macOS Release artifact。
