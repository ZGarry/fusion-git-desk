# Fusion Git Desk 需求规划

## 产品定位

面向同时维护多个代码仓库的开发者、集成负责人和交付人员，提供一个桌面端多仓库 Git 工作台。它不替代专业 IDE，也不追求覆盖所有 Git 命令，而是聚焦跨仓库状态聚合、风险识别、安全同步、diff 快速巡检和小步提交闭环。

一句话定位：让用户在一个窗口里看清很多仓库的 Git 状态，并安全地完成“检查、同步、暂存、提交”的基础工作。

## 核心作用

- 降低多仓库巡检成本：不用在多个终端里反复进入目录执行 `status`。
- 降低批量同步风险：默认把 `fetch` 和会改工作区的 `pull` 分开，`pull` 只对干净仓库执行 fast-forward。
- 降低 diff 检查成本：选中仓库和文件后直接查看 working、staged、HEAD 视图。
- 降低小步提交摩擦：在同一个上下文里完成文件级 stage/unstage 和 staged commit。
- 提升问题可解释性：把冲突、无 upstream、本地改动、远端落后、命令失败等状态暴露给用户。

## 核心能力

- 自动发现工作区下多个 Git 仓库
- 展示仓库状态、分支、远端、ahead/behind、最后提交
- 支持批量 fetch 和仅干净仓库 pull
- 支持 working/staged/HEAD diff
- 支持点击变更文件查看文件级 diff
- 支持对当前选中文件执行 stage/unstage，并在操作后刷新仓库状态和 diff
- 支持当前仓库 commit 草稿，对已暂存文件提交并刷新状态
- 对未跟踪文本文件生成新增文件 diff 预览
- 对无文本 diff 的变更展示原因说明

## 基础闭环优先级

当前阶段优先完善基础能力，不优先展开深度功能。每轮需求选择前先检查这些问题：

1. 扫描是否可靠：能否发现工作区内仓库，并在失败时说明原因。
2. 状态是否可信：分支、远端、ahead/behind、本地改动、冲突和 upstream 状态是否清楚。
3. diff 是否可用：大多数普通仓库能否稳定查看仓库级和文件级 diff。
4. 同步是否安全：fetch、pull、自动 pull 的边界是否显式，并保护脏工作区。
5. 小步提交是否闭环：stage/unstage/commit 是否只作用于当前仓库和明确文件。
6. 验证是否成立：改动是否有自动测试、构建或可重复手动验收方式。

只要这些基础闭环里存在 P0/P1 问题，就不应优先做后台托盘、复杂分组、深层缓存、复杂发布体验等深入事项。

## 值得优化的问题

- P0：会破坏用户工作区、导致数据丢失、构建测试发布失败、核心流程无法使用的问题。
- P1：用户在日常多仓库巡检中反复遇到的卡顿、误解、错误不可见、安全边界不清或操作闭环断裂。
- P2：明确提升效率但不影响基础闭环的体验改进，例如过滤、排序、轻量提示和文档补强。

暂不值得优化的问题：

- 没有用户场景或测量依据的深度性能重构。
- 为未来大功能提前铺设的大抽象。
- 会扩大 Git 写操作范围但没有足够保护和验收的功能。
- 只让内部结构更漂亮、但不改善用户基础流程的改动。
