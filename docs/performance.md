# Fusion Git Desk 性能审计与优化记录

状态日期：2026-06-10

## 结论

当前架构对几十个普通 Git 仓库已经够用，但在以下场景中仍需要主动限流：

- 工作区包含大量仓库，且每个仓库都要执行多条 Git 命令。
- 仓库里存在很大的未跟踪目录，例如未忽略的构建产物或依赖目录。
- 单个仓库有大 diff，前端一次性渲染过多文件和行。
- 自动刷新、自动 fetch、自动 pull 与手动操作同时发生。

本轮优化优先处理最容易造成卡顿的路径：状态扫描、未跟踪文件预览、diff 渲染和前端派生计算。

## 本轮已完成优化

### Git 状态扫描

- 将常规 `git status` 的未跟踪模式从 `-uall` 调整为 `-unormal`。
- 目的：避免未跟踪目录被递归展开成海量文件行。
- 影响：已存在目录中的新文件仍会显示；完全未跟踪目录会以目录项显示。

### 只读 Git 命令

- 所有 Git 子命令增加 `--no-optional-locks`。
- 目的：减少后台扫描和刷新时对 Git index 可选锁的干扰，降低与用户手动 Git 操作互相影响的概率。

### 未跟踪文件 diff

- 全量 working diff 不再读取前 30 个未跟踪文件内容。
- 全量视图只生成 metadata 摘要。
- 文件内容预览保留在文件级 diff 中，用户选中具体未跟踪文件后再读取。
- 目的：避免一次打开 diff 就读取大量磁盘内容、分配大量 diff 行对象。

### 前端渲染

- 仓库统计从多次 `filter` 改为一次遍历。
- 当前仓库查找从线性 `find` 改为 `Map` 派生索引。
- 变更文件列表限制为前 600 项渲染。
- 变更文件列表增加文件名过滤，渲染上限应用到过滤结果，便于在大变更仓库中先缩小候选文件。
- diff 渲染限制为前 80 个文件、前 4000 行。
- 目的：防止 WebView 因超大 diff 或超多变更文件产生过多 DOM 节点。

### 变更文件过滤

- 优化前的问题：当单仓库存在数百个变更文件时，右侧列表只能靠滚动查找，定位目标文件很慢。
- 采取的策略：在“变更文件”面板增加文件名过滤输入，仅对当前仓库的变更文件做前端派生过滤，再应用现有 600 项渲染上限。
- 性能取舍：增加了一次面向当前仓库变更列表的本地过滤计算，但避免了用户在大列表中反复滚动和误点，不引入新的后端 I/O。
- 验收方式：`cd frontend && pnpm build`、`go test ./...`，并手动确认过滤后计数、空状态和渲染上限提示都正确。

### 自动周期调度

- 手动扫描、单仓刷新、批量 `fetch/pull` 之间增加前端 busy guard，避免同时触发多组 Git 命令。
- 自动周期遇到扫描或批量更新占用时，不再静默跳过，而是显示最近一次跳过原因和执行时间。
- 自动 `fetch/pull` 的最近一次运行结果细化为成功、跳过、失败计数；无仓库时显示待命，不再落成模糊的“结束”提示。
- 自动周期新增连续失败计数和首个失败原因展示，连续失败 3 次后升级为更强的危险态提示。
- 自动周期补充最近 10 分钟失败窗口统计；如果失败已经恢复但短时间内仍反复出现，状态栏会继续提示短时抖动。
- 目的：减少后台任务重叠造成的 Git 子进程堆积，并让“为什么这次没刷新”变得可观察。

### Pull 跳过提示

- 优化前问题：开启“仅干净仓库 Pull”后，有本地改动的仓库会被保护性跳过，但状态栏只显示跳过数量，用户容易误以为 Fetch 也被禁止。
- 采取策略：Pull 跳过时在顶部状态和最近更新中展示“工作区有本地改动”的原因，并在仓库标题区提示 Fetch 仍可更新远端引用。
- 性能取舍：只增加前端字符串派生和一条后端中文消息，不新增 Git 调用。
- 验收方式：在有本地改动的落后仓库上点击 Pull，应提示跳过原因；点击 Fetch 应继续执行远端引用更新。

### 仓库健康与操作预检

- 优化前问题：多仓库工作区虽然已经扫描出落后、领先、冲突、无 upstream 和本地改动，但这些状态分散在标签中，用户点击 Pull 或切换分支前仍需要自己推断风险。
- 采取策略：前端增加仓库关注优先级排序、顶部冲突/无上游/Pull 保护指标、仓库行风险标签、选中仓库“状态建议”面板，以及 Pull/切分支按钮 title 预检说明；后端 Pull 对冲突和无 upstream 统一返回跳过原因。
- 性能取舍：复用现有 `Inspect` 结构化状态，不新增 Git 命令；新增的排序和建议仅为本地数组派生，适合当前仓库规模。
- 验收方式：`cd frontend && pnpm build`、`go test ./...`，并在 demo 状态下确认状态建议、Pull 保护和工作区满高布局正常。

### 文件级暂存操作

- 优化前问题：用户在 diff 中确认某个文件后，仍需要回到命令行执行 `git add` 或取消暂存，代码查看和提交整理之间断开。
- 采取策略：前端在当前文件条提供 Stage/Unstage 显式按钮；后端只允许操作当前变更列表中的仓库内路径，并在完成后刷新仓库状态和 diff。
- 性能取舍：每次文件级操作会增加一次 Git index 命令和一次仓库刷新，换取明确的状态闭环；操作期间会阻止扫描、pull/fetch 和切分支，避免并发改 index。
- 验收方式：`go test ./...` 覆盖 stage/unstage 与路径边界；`cd frontend && pnpm build` 验证前端类型和构建。

### 当前仓库提交草稿

- 优化前问题：Stage/Unstage 后仍只能在外部命令行提交，用户无法在同一个代码巡检上下文内完成小步提交。
- 采取策略：右侧增加“提交草稿”面板，仅在当前仓库存在 staged 文件且提交消息非空时允许 Commit；后端提交前检查冲突和 staged 数量，提交后刷新仓库状态并切到 HEAD diff。
- 性能取舍：提交会执行一次 `git commit` 和一次仓库刷新；提交期间会阻止扫描、pull/fetch、切分支和文件暂存操作，避免并发修改 index。
- 验收方式：`go test ./...` 覆盖 staged commit 和无 staged 文件拒绝；`cd frontend && pnpm build` 验证前端类型和构建。

### 扫描耗时指标

- 优化前问题：多仓库扫描会串起 `rev-parse`、`status`、`remote get-url`、`log -1` 等 Git 调用，但界面只能看到最终状态，难以判断慢在状态扫描、远端信息还是最后提交读取。
- 采取策略：后端 `Inspect` 为每个仓库返回 `revParseMs`、`statusMs`、`remoteMs`、`lastCommitMs` 和 `totalMs`；前端在仓库列表和仓库摘要中显示紧凑的 `Scan` 耗时，悬停展示分项。
- 性能取舍：本轮只增加 `time.Since` 级别的本地计时，不新增 Git 调用，也不改变扫描并发、timeout 或 `--no-optional-locks` 策略；耗时指标会略微增加 JSON 字段大小。
- 验收方式：运行 `cd frontend && pnpm build`、`go test ./...`，并在扫描后确认仓库行可以看到 `Scan xxms`。

## 性能取舍

- `-unormal` 比 `-uall` 更适合常规多仓库巡检，因为它避免了未跟踪目录递归爆炸。
- 全量 diff 牺牲了“未跟踪文件内容立即展开”，换来更稳定的首次加载性能。
- 文件级 diff 仍保持完整预览能力，因此深查某个文件的能力没有移除。
- 变更文件过滤仍会对当前仓库的变更数组做一次轻量字符串匹配，但能把实际 DOM 渲染和人工定位成本压到更小范围。
- 变更文件过滤保留了完整数据集，只在视图层收窄范围，因此不会影响 diff 与分支数据加载逻辑。
- 前端渲染上限不是最终虚拟滚动方案，但配合过滤能先阻断最坏情况下的 UI 卡死。

## 后续建议

- 给 diff 面板接入真正的虚拟滚动，替代固定渲染上限。
- 给变更文件列表增加虚拟列表。
- 评估把 `Inspect` 中的 `remote get-url` 和 `lastCommit` 做成延迟加载，首屏先返回状态。
